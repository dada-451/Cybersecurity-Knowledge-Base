# OpenHarmony 编译、屏幕与触摸适配复盘

这篇记录我从基线编译、PAC 打包到屏幕与触摸跑通的过程，重点保留遇到的问题和排查思路。

## 编译环境、系统构建与 PAC 打包

我最开始的任务是编译 OpenHarmony 基线并烧录到目标设备。环境是在 Windows 上用 VMware 运行 Ubuntu，编译在虚拟机里进行，PAC 通过共享目录交给 Windows 侧下载工具使用。

### 当时使用的目录

| 用途              | 路径                                                 |
| ----------------- | ---------------------------------------------------- |
| 工程根目录        | `/work/uis7885`                                      |
| 产品镜像目录      | `/work/uis7885/out/wukong100/packages/phone/images/` |
| PAC 脚本目录      | `device/board/revoview/wukong100/pac/`               |
| 平台打包资源      | `device/soc/unisoc/p7885/pac/ImageFiles/`            |
| Windows 共享目录  | `D:\image`                                           |
| Ubuntu 共享挂载点 | `/mnt/hgfs/image`                                    |

这些路径属于当时的企业工程，并不是所有 OpenHarmony 工程通用的目录。

### 从基线编译到打包

历史记录出现过下面两种构建命令：

```bash
./build.sh --product-name wukong100 --ccache
./build.sh --product-name wukong100 --ccache --gn-args make_custom_image=true -j8
```

它们记录的是不同阶段的使用方式，不能直接当成其他设备的通用构建教程。后一个命令涉及该企业工程的镜像构建参数；换工程时需要先检查构建脚本和产品配置。

我曾经已经生成 `system.img`、`vendor.img` 等镜像，却在 PAC 打包时遇到依赖文件缺失。排查时重点检查了厂商固件依赖与 `ImageFiles` 资源目录。这类问题需要逐项核对缺失文件、脚本输入路径和资源版本，区分资源未准备、路径错误和版本不匹配。

历史打包调用形式如下，执行前需要确认输入已经准备完整：

```bash
cd /work/uis7885/device/board/revoview/wukong100/pac
bash uis7885_pac.sh /work/uis7885/out/wukong100/packages/phone/images /work/uis7885/device/soc/unisoc/p7885/pac/ImageFiles
```

我曾在排查中尝试从资源目录补充镜像。复盘时，我不把“同名文件复制过去”当成通用解决方法：旧的 `boot.img`、`vendor_boot.img` 或 `dtbo.img` 可能重新带入旧内核和设备树，必须确认版本和来源。

### 烧录异常怎样看

早期遇到过 `Uart send error`、下载工具错误码以及设备没有反应等现象。我还做过对照：其他 Android PAC 能下载成功，而自己生成的包失败。

这个对照只能说明设备和下载链路在某种组合下可用，帮助把注意力转向 PAC 的兼容性、下载代理和镜像组合；不能直接证明某一份 FDL 一定错误。这些下载异常未逐项保留完整定位结论。

更关键的是，下载工具显示 `Passed` 后，设备仍然可能黑屏或者内核崩溃。刷写通过只是一个阶段结果，后面还需要检查启动日志、系统界面和实际功能。

### 源码修改为什么可能没有生效

工程中既有正式源码，也有 `out/.../src_tmp` 构建副本。我曾经在正式源码里修改了面板映射，但实际单编使用的副本没有同步；也出现过只改副本而正式源码仍保留旧配置的情况。

我后来把核对范围扩展为：

```text
正式源码 → 实际构建副本 → LK / 内核 / DTB 产物
        → 打包 images 目录 → PAC → Windows 侧刷机文件
```

记录中保留了源码与副本的 `diff`、新 LK 文件的时间戳，以及把新生成的 `lk-sign.bin`、`lk-fdl2-sign.bin` 放入打包目录的操作。具体需要更新哪些文件，取决于本次改动和打包脚本，不能只更新其中一个就假定整包是新的。

### 共享目录与空间问题

共享目录曾出现挂载、访问权限、当前目录不正确等问题。文件在 `/mnt/hgfs/image`，不代表它已经复制到 `/work`。我还遇到过受权限影响的通配符匹配问题，所以不能看到一次“找不到文件”就断定文件不存在。

PAC 记录大小约 4.5 GB。复制后可以比较两端大小和 SHA-256：

```bash
sha256sum /work/uis7885/out/wukong100/packages/phone/images/wukong100_nosec_userdebug.pac /mnt/hgfs/image/wukong100_nosec_userdebug.pac
```

这属于完整性核对方法，现有记录没有证明当时一定发生过共享目录静默损坏。

我也花了不少时间处理虚拟机磁盘不足。后来才分清：客体文件系统可用空间、虚拟磁盘文件大小和 Windows 宿主机可用空间不是同一个数。为了腾空间随意删除构建目录，还可能造成后续需要重建。

### 现在回看，我会怎么组织构建记录

每次交付镜像时，我会把源码版本、修改文件、构建命令、生成时间、PAC 文件名和校验值一起记录，再关联对应的设备现象。这里是我复盘后准备采用的做法，不代表当时已经有一套完整自动化构建流水线。


## HX8394F 屏幕驱动移植与调试

屏幕适配是我这次项目的主要工作。企业提供了 Android BSP 和在 OpenHarmony 6.1 上点亮屏幕、触摸的参考补丁。我把相关代码和配置集成到目标工程，再通过编译、打包和实机反馈逐步排查。

### 我实际检查过的位置

- LK 面板驱动和 `panel_cfg.h` 中的面板选择表。
- LK 的产品编译配置 `uis7885_2h10.mk`。
- 内核中的 `uis7885-2h10-overlay.dts` 和 LCD DTSI。
- `ums9620.dtsi`、`i2c.dtsi` 等设备树包含关系。
- `out/wukong100/lk/src_tmp` 和内核构建副本中的对应文件。
- 新生成的 LK、DTB 及打包输入目录。

我先后遇到了启动后不亮、显示异常和白屏崩溃。这些现象出现在多轮修改中，不能简单理解为每种现象都只对应一个原因。

### 问题一：屏幕 ID 映射到了占位驱动

烧录通过后，屏幕仍不能正常显示。我开始沿着 LK 的面板选择表检查 ID 和驱动的对应关系。

记录中有一轮修正是把 `0x3821` 对应的驱动由 `dummy_mipi_driver` 改回 `lcd_hx8394f_mipi_driver`。保留的检查结果如下：

```c
.lcd_id = 0x3821,
.drv = &lcd_hx8394f_mipi_driver,
```

同事提供的设备启动参数还出现过：

```text
lcd_id=ID3821
lcd_name=lcd_hx8394f_mipi_himax
lcd_size=1136x640
```

这说明那次启动参数已经指向目标面板，但单凭这些参数还不能证明显示链路全部正常。

早期我也尝试过把末尾 `0xFFFF` 的 dummy 兜底项直接指向真实屏驱动。后来保留的检查结果显示，目标 ID 使用真实驱动，兜底项仍使用 dummy。我现在更认可按目标 ID 修正映射，而不是把所有未知面板都强制套到一块屏上。

### 问题二：LK 和内核显示配置没有一起核对

LK 阶段选中了目标屏幕，不代表内核阶段一定继续使用正确配置。在一次检查中，内核 overlay 同时包含了：

```dts
#include "lcd/lcd_hx8394f_mipi_himax.dtsi"
#include "lcd/lcd_dummy_mipi.dtsi"
```

后续复盘把乱码、卡死等现象与两阶段配置不一致、占位屏配置残留联系起来。我的处理方向是统一 LK 的驱动选择与内核显示配置，并确认修改进入实际构建使用的文件。

显示异常出现在多轮调试中，排查时同时核对面板选择、设备树配置和实际构建输入。

工程中还出现过 `SPRD_DOUBLE`、ILI9881D 编译项和第二路 reset 配置。我曾尝试关闭相关项，但后来发现没有硬件依据时不应直接认定它们多余。看到多套屏配置，仍需要结合原理图、BOM 或企业说明确认用途。

### 问题三：白屏后崩溃，排查 I2C3 时钟配置

后期设备有背光，但白屏并出现崩溃。后续记录将内核错误描述为 `SError`，排查重点转向设备树中的 I2C3 配置。

当时 `ums9620.dtsi` 中，在包含 `i2c.dtsi` 后又追加了一段 `&i2c3` 配置：

```dts
#include "i2c.dtsi"
&i2c3 {
    clock-names = "enable", "i2c", "source";
    clocks = <&apapb_gate CLK_I2C3_EB>, <&ap_clk CLK_AP_I2C3>, <&ext_26m>;
};
```

这段额外定义成为重点检查对象。后续修改移除了冲突覆盖，并核对正式源码和内核构建副本。这里的问题是重复配置中的属性覆盖关系，不是说设备树只要再次引用同一个节点就一定有错。

为了确认改动进入产物，我还尝试反编译生成的 DTB：

```bash
./scripts/dtc/dtc -I dtb -O dts mkboot/dist/ums9620-base.dtb > /tmp/base_check.dts
```

当时用 `grep` 搜索过 `apapb_gate`、`apahb_gate`、`i2c3`，但输出没有匹配到这些名字。回看时，这一步不能单凭“计数为 0”就当成修复证据：DTB 反编译后可能以地址和 phandle 表示引用，源文件里的标签不一定保留。应继续按节点地址和引用关系查看实际属性。

这轮排查包含 I2C3 配置修正、源码与构建副本同步、产物更新和重新打包。8 月 15 日设备最终进入 OpenHarmony 界面。由于修正涉及多个环节，现有记录不足以将全部现象归因于单一改动。

### 问题四：源码修正后，设备现象仍然不变

这是我最容易忽视的一点。正式源码、LK 的 `src_tmp`、内核的 `src_tmp`、`mkboot/dist` 和打包镜像目录不是同一个位置。

记录里有正式源码和副本不一致的情况，也有重新构建之后仍怀疑 PAC 没更新的情况。最后我不再只检查“源码是不是改对了”，而是继续核对副本、产物时间戳、打包输入和刷机包。

### 验证结果与局限

8 月 15 日 23:46，我记录“成功进去了”，随后确认是 OpenHarmony 界面。结合后续项目总结，屏幕和触摸基本操作已跑通。

目前保留的是功能验证与排障记录，没有足够资料支持帧率、长时间稳定性和所有显示模式的结论。如果重新做一次，我会为每个镜像保留版本、校验值、启动日志和实机照片，把每轮变化对应起来。


## CHSC5xxx 触摸模块集成与验证

触摸和屏幕一起由我负责。我的工作以企业提供的参考代码为起点，把 CHSC5xxx 相关文件集成到目标内核工程，再结合设备树和编译配置完成适配。

### 留存的操作记录

7 月 27 日的记录保留了把参考补丁中的 `chsc5xxx` 文件复制到下面目录的操作：

```text
kernel_unisoc_p7885/drivers/input/touchscreen/chsc5xxx/
```

文件包括 `Kconfig`、`Makefile`、`i2c_communication.c`、`semi_touch_device.c`、`semi_touch_function.c` 等。这些文件来自企业参考补丁，我负责在目标内核工程中的集成与适配。

### 我对触摸链路的理解

```text
触摸芯片 → I2C 通信 → 驱动读取触点数据 → Linux 输入事件 → 系统响应操作
```

移植时需要关注驱动是否参与编译、设备描述是否匹配，以及电源、复位、中断和坐标配置是否符合目标设备。

本文保留集成路径与基本功能结果，未收录最终的全部设备树差异和输入事件日志。

### 已确认的结果

基于企业参考补丁完成 CHSC5xxx 触摸模块集成后，目标设备能够进行基本触摸操作。

当前验证范围为基本触摸操作。后续测试计划包括多点触控、边缘区域、长时间操作、重启及休眠唤醒，并保留对应输入事件。


## 技术总结

这次适配让我逐步把调试范围从单个驱动文件扩展到完整构建与运行链路：

- 构建、打包、烧录、系统启动和功能验证分别检查，每个阶段保留对应结果。
- 同时核对正式源码与实际构建副本，避免修改停留在未参与编译的目录。
- 将 LK、内核设备树、打包镜像和实机现象关联起来，检查配置是否贯穿启动过程。
- 反编译 DTB 后按实际节点和 phandle 检查属性；标签搜索和时间戳只作为辅助信息。

最终完成了目标设备的系统启动、屏幕显示和基本触摸操作验证。后续可继续补充镜像版本记录、启动日志、实机照片与稳定性测试数据。
